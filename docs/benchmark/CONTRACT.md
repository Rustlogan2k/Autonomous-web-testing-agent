# Benchmark application contract

What an application must be to join the benchmark suite, and why each rule exists.
An application that follows this document is admitted by one command:

    python scripts/validate_benchmark.py --apps <app_id> --settle-quiet-ms 80 --random-steps 600

The validator is the authority. If this document and the validator disagree, the
validator is right and this document has a bug.

---

## 1. What an application is for

Each application is a small, self-contained web application with a **clean build** and a
**faulty build** that differs from it only by a few seeded functional faults. A testing
agent explores the faulty build through a real browser. A deterministic oracle watches and
confirms a fault when the agent's own actions make it observable.

The faults are **semantic and silent**: the page loads, returns 200, logs nothing, and
shows the wrong thing. A fault that throws a console error or returns a 404 is found by a
pattern matcher and measures nothing about exploration.

The suite exists to measure **generalization across applications**, so applications must
genuinely differ: in workflow shape, in how state is held, in DOM idiom, and in
vocabulary. An agent that learned one application's button labels must gain nothing from
them on the next.

## 2. Layout

    tests/fixtures/benchmark/<app_id>/
        clean/            the application, correct. Hand-written. `index.html` is the entry.
        buggy/            GENERATED by build.py. Never edit by hand.
        build.py          declares the patches; delegates to the shared builder
        faults.json       fault library, reachability witnesses, benign traces, regions

`build.py` is this, with your own patches:

```python
"""Seeded faults for <app name>. Run to regenerate buggy/; --check verifies it is in sync."""
from web_testing_agent.benchmark.builder import Patch, main

PATCHES = (
    Patch(
        fault_id="BOOK-01",
        filename="assets/app.js",          # path relative to clean/
        find="var total = rate * nights;",  # must occur EXACTLY ONCE in that file
        replace="var total = rate * (nights - 1);",
        why="calculation error: the final night is not charged",
    ),
)

if __name__ == "__main__":
    raise SystemExit(main(__file__, PATCHES))
```

A fault may need more than one patch; give them the same `fault_id`. Run it with the
project interpreter: `venv/Scripts/python.exe tests/fixtures/benchmark/<app_id>/build.py`.

## 3. Technical rules for the application

Served as static files by a plain HTTP file server, one origin per build.

- **Static only.** HTML, CSS, and vanilla JavaScript. No backend, no build step, no
  framework, no package manager.
- **Fully offline.** No CDN, no web fonts, no external images, no analytics. Every request
  must resolve inside the application's own directory. An unresolved request is an HTTP
  error, and the harness treats that as a finding.
- **Relative URLs only**, so the application works from any origin and port.
- **No links that leave the application** and no `target="_blank"`.
- **Zero console errors and zero failed requests, on both builds**, on every page and
  after every action. Include a `favicon.ico` (or a `<link rel="icon" href="data:,">`) so
  the browser's automatic favicon request does not 404.
- **State lives in `sessionStorage` or in memory.** Every episode starts in a fresh
  browser context, so both are empty at the start of each episode; that is the reset.
  A fault that must survive a reload needs `sessionStorage`.
- **Deterministic.** Nothing rendered may depend on the clock, the date, or
  `Math.random()`. The same action sequence must produce byte-identical pages every time.
- **Synchronous.** No `setTimeout`/`setInterval`/animation that changes the DOM after the
  event handler returns. The harness treats the page as settled 80 ms after the last DOM
  mutation; anything that arrives later is attributed to the wrong step.
- **No native dialogs.** `alert`, `confirm` and `prompt` are dismissed automatically by
  the browser driver, so a flow that depends on one can never proceed. Build confirmations
  as ordinary in-page panels with buttons.

## 4. What the agent can do (this bounds what a fault may require)

The agent's action space is rebuilt from the DOM on every step. It contains exactly:

| Action | Generated for | Notes |
|---|---|---|
| CLICK | every visible, enabled `<a href>`, `<button>`, `<input type=button\|submit>` | label = the element's visible text, cut at 60 characters |
| CLICK (toggle) | every `<input type=checkbox\|radio>` | one action per control |
| TYPE | every `<input>` (text-like) and `<textarea>` | **five fixed values per field**, see below |
| SELECT | every `<select>` | up to **four** options: the last, then the first three |
| RAPID_CLICK | every `<button>` and submit input | five clicks in a burst |
| fixed | scroll up/down, resize viewport ×3, back, forward, refresh, no-op | always present |

Consequences you must design around:

- **Only those five element kinds are actionable**: `input`, `textarea`, `select`,
  `button`, `a[href]`. A `<div onclick>`, a `<label>`, a `<summary>`, an `<a>` without
  `href`, or anything with `role="button"` is invisible to the agent. Use real controls.
- **No hover, no key presses (no Enter to submit), no drag, no file upload.**
- **At most 91 page actions survive**, allocated clicks first. A page with 40 buttons
  leaves little room for its form fields. Keep each page or view to roughly **10–40
  interactive controls**.
- **Hidden and disabled controls are not actions.** Revealing or enabling a control
  (a gate) is a legitimate and encouraged design element.
- **The values the agent can type are fixed**, chosen by the input's `type`:

| `type` | valid_typical | boundary_min | boundary_max | empty_string | type_mismatch |
|---|---|---|---|---|---|
| text | `Test User Input` | `a` | 2,048 × `A` | `` | `12345` |
| email | `tester@example.com` | `a@b.co` | 240 × `a` + `@example.com` | `` | `not-an-email` |
| number | `42` | `0` | `999999999` | `` | `not-a-number` (the browser refuses it) |
| tel | `+1-202-555-0143` | `1` | 32 × `1` | `` | `not-a-phone-number!!` |
| url | `https://example.com/page` | `http://a.co` | long URL | `` | `not a url` |
| password | `CorrectHorseBattery9!` | `a` | 2,048 × `A` | `` | one space |
| date | `2026-06-15` | `0001-01-01` | `9999-12-31` | `` | `not-a-date` |
| search | `search query` | `a` | 2,048 × `A` | `` | tab + newline |
| textarea | two-line comment | `a` | 8,192 × `A` | `` | `12345` |

  Any validation gate on the path to a fault **must be passable with these values**. A
  number field that only accepts 1–20 can never be satisfied (the only in-range candidate
  is 42 — so the range must include 42, or 0). This exact mistake was made once already.

- **Every form control needs a `name`** that is a plain identifier (`nights`,
  `guest_email`), a unique `id`, and a visible `<label for=...>`. The `name` is how the
  oracle refers to what the user entered. Radio buttons in a group share a `name`; give
  each its own `id`.
- Give every button and link that matters a unique `id` as well. It makes replay exact.

## 5. Seeded faults

Each application seeds **exactly two faults, of two different classes**. The classes are
fixed by the project's pre-registration:

| Class | Definition |
|---|---|
| `state_corruption` | a value the user supplied is altered or lost across a transition |
| `constraint_bypass` | a validation rule the application declares is not enforced |
| `broken_transition` | a control that should change state does not, or reaches the wrong state |
| `calculation_error` | a derived value shown to the user is wrong given its inputs |
| `persistence_failure` | a committed change is not reflected on re-read |

Requirements for each fault:

1. **Silent.** No console error, no failed request, no visibly broken page.
2. **Reachable only by using the application.** The shortest triggering action sequence
   should be **6 to 10 actions** from the entry page, and should pass through at least
   one form or gate. A fault visible on the landing page measures nothing.
3. **Not triggered by the correct default walk.** At least one action on the path must be
   a specific choice (a non-default value, a particular option, a particular order of
   operations), so that a walk through the workflow that changes nothing does not trip it.
4. **Deterministic.** The same sequence triggers it every time.
5. **Observable as text in a named page region** (section 6).
6. **Independent of the other fault** where practical: triggering one should not require
   triggering the other.

Do not make the fault harder by hiding controls below the fold or burying them among
dozens of identical buttons. Difficulty should come from the *workflow*, not from noise.

## 6. The oracle, and how to write an assertion it can check

The oracle reads the **page text the agent observed** and nothing else. It never executes
code from the fixture. A fault is described by one or more assertions; **all** must be
violated, and none inconclusive, for the fault to count as observed.

An assertion states the **expected behaviour**. It is *violated* when the page deviates.

```json
{
  "kind": "echoes_input",
  "where": "confirmation\\.html",
  "region": "confirm_quantity",
  "input_field": "quantity",
  "describes": "the confirmation must echo the quantity entered on the product page"
}
```

- `where` — a regex on the step's URL. The **last** matching step is the one judged. For
  an application whose URL never changes, use `".*"`.
- `region` — a name defined in the manifest's `regions` map, which maps it to a selector.
  Supported selectors: `#id`, `.class`, or a bare tag. The **first** match is read.
  - The region must be a **leaf-like element**: it must not contain another element of
    the same tag (a `<td>` inside a `<td>`, a `<span>` inside a `<span>`).
  - **A region that is absent makes the assertion inconclusive, not violated.** Use this:
    render the region only in the state where the fault is observable. In a single-page
    application, build each view's DOM when the view is shown rather than keeping every
    view in the document and hiding it — a hidden stale region is still read.
  - The oracle reads text content. It cannot read an input's value or a checkbox's state,
    so echo what matters as text.

| `kind` | Expected behaviour (violated when it does not hold) | Extra fields |
|---|---|---|
| `text_equals` | region text equals `expected` | `expected` |
| `text_contains` | region text contains `expected` (case-insensitive) | `expected` |
| `text_absent` | region text does not contain `expected` | `expected` |
| `echoes_input` | region text contains the value last **successfully** entered into the field | `input_field` = the control's `name` |
| `numeric_equals` | some number in the region equals `expression` | `expression` over field names, `+ - * /` and constants, e.g. `"nights * 85 + 12"` |
| `url_matches` | the step's URL matches `expected` (regex) | `expected` |
| `region_empty` | the region has text; **violated when it is blank** | — |
| `reached_with_invalid_input` | violated when the entered value matches `expected` (regex for *invalid*) | `input_field`, `expected` |

Notes that save time:

- For a SELECT, the recorded input is the option's **`value` attribute**, under the
  select's `name`. Make option values meaningful (`value="3"` for three nights).
- `numeric_equals` needs every variable in the expression to have been entered and to
  parse as a number; otherwise it is inconclusive. Any number in the region matching is
  enough, so keep the region to the one value.
- `text_contains`/`text_equals` mean "must". To say "this warning must be shown", use
  `text_contains`; it is violated when the warning is missing.
- A typical `constraint_bypass` is two assertions: `reached_with_invalid_input` (or
  `region_empty`) on the page that should have been refused.

**The clean-build control.** The oracle replays every candidate on the clean build and
rejects it if the assertion fires there too. So an assertion that sometimes fires on a
correct application does not produce false findings — but it does waste verification
time, and it must never fire on your reachability witness or your benign trace. Design
the region so that ordinary use of the clean build leaves the assertion silent.

## 7. `faults.json`

```json
{
  "app_id": "booking_desk",
  "name": "Human-readable product name",
  "entry": "index.html",
  "regions": { "summary_total": "#summary-total" },
  "faults": [
    {
      "fault_id": "BOOK-01",
      "fault_class": "calculation_error",
      "description": "What is wrong, in one or two sentences.",
      "trigger_condition": "What a user must do for it to become observable.",
      "expected_behaviour": "What a correct application shows.",
      "observable_violation": "What the faulty build shows instead.",
      "assertions": [ { "kind": "numeric_equals", "where": ".*", "region": "summary_total",
                        "expression": "nights * 85", "describes": "..." } ],
      "reproduction": { "replays": 2, "must_all_reproduce": true },
      "minimization_keep": [],
      "observation_horizon": 2,
      "shortest_path": 7,
      "trigger_trace": [
        { "type": "CLICK", "id": "start-booking" },
        { "type": "SELECT", "id": "nights", "params": { "option": "3" } },
        { "type": "TYPE", "id": "guest_email", "params": { "category": "valid_typical" } },
        { "type": "CLICK", "text": "Review reservation" }
      ]
    }
  ],
  "benign_traces": [ [ { "type": "CLICK", "id": "start-booking" } ] ],
  "characterization": { "pages_or_views": 0, "workflow_state_representation": "" }
}
```

**Trace steps.** `type` is one of `CLICK`, `TYPE`, `SELECT`, `RAPID_CLICK`, `REFRESH`,
`BROWSER_BACK`, `BROWSER_FORWARD`, `SCROLL`, `RESIZE_VIEWPORT`. A control is named by
`id` (its DOM id — preferred), or `text` (a case-insensitive substring of its visible
label), optionally with `nth` (0-based) when several controls match. TYPE takes
`params.category`, one of the five category names above — never a literal value. SELECT
takes `params.option`, the option's `value`. A toggle is a `CLICK` on the checkbox's id.

- `trigger_trace` — the **reachability witness**: one sequence that triggers the fault on
  the faulty build. It must not trip the assertion on the clean build. It is never shown
  to any agent.
- `benign_traces` — at least one sequence that completes the application's main workflow
  **correctly** and trips no assertion on either build.
- `observation_horizon` — number of state transitions between the triggering action and
  the step where the violation becomes visible.
- `shortest_path` — your best estimate; the validator reports the minimized length.

## 8. Definition of done

The validator prints `ADMITTED` for the application. Specifically, in a real browser:

- the manifest is well formed and `buggy/` is exactly `clean/` plus the patches;
- each witness replays with no unresolved step, fires on the faulty build, is silent on
  the clean build, is confirmed by the oracle, and its minimized form still fires;
- each benign trace replays cleanly and is silent on both builds.

With `--random-steps 600` it also reports two numbers worth looking at:

- **clean raw candidates** — how often the assertions fired under random exploration of
  the *correct* build. Aim for 0. A high number means the region is present in states
  where it should not be.
- **faulty first verified** — how far uniform-random exploration got. If random clicking
  confirms a fault within a few dozen steps, the fault is too shallow.
