\label{chap.1}

\section{Motivation}

Web applications carry much of everyday business: shops, banking, booking, support desks,
internal tools. Their functional faults are rarely crashes. More often a page shows the
wrong total after a quantity changes, accepts an input on one path that it rejects on
another, or loses a value when the page is reloaded. Such faults sit behind sequences of
interactions: a user must sign in, fill a form, reach a review step, go back and change
something. A tester has to perform the right sequence and then notice that the result is
wrong.

Writing scripted end-to-end tests for every such sequence is expensive, and the scripts
cover only what their authors thought of. Automated exploratory testing instead drives a real
browser through the application and searches for misbehaviour. The simplest explorer clicks
at random. More capable explorers learn where to go, and reinforcement learning (RL) is a
natural fit: the tester is an agent, the application is its environment, and reaching new or
suspicious behaviour can be rewarded. Several RL web testers have been published, including
WebExplor~\cite{zheng2021webexplor}, WebQT and
WebRLED~\cite{gu2025webrled}.

Two problems limit these testers. The first is \emph{where to go}. The decisive actions are
often many steps into a workflow, the set of available actions changes on every page, and a
reward based on novelty pays for reaching new pages, not for testing them. The second is
\emph{what counts as a fault}. Published RL web testers report errors in the browser console
as failures~\cite{zheng2021webexplor, gu2025webrled}. That is an implicit
oracle~\cite{barr2015oracle}: it cannot see a page that renders the wrong content without an
error, and it cannot say whether a reported error is reproducible or matters.

\section{Problem statement and research questions}

The project began by asking whether deep reinforcement learning can learn to find
functional bugs in web applications. The first generation of the tester answered part of
that question negatively (Chapter~\ref{chap.4}), and the question that the thesis as a whole
answers became broader:

\begin{quote}
\emph{How much do exploration structure, lightweight online learning and reliable fault
verification each contribute to autonomous functional web testing?}
\end{quote}

This breaks down into four research questions:
\begin{description}[noitemsep]
  \item[RQ1] Does a deep RL tester learn state-dependent behaviour, and does pretraining on
        other applications transfer to a new one?
  \item[RQ2] Is a small local LLM a useful source of reward or page labels for testing?
  \item[RQ3] Does a structured exploratory tester verify more functional faults than random
        exploration, and does adding online learning to it improve it further?
  \item[RQ4] How does the tester compare with published RL web testers on their own
        applications and measures, and what limits it there?
\end{description}

A fault is \emph{verified} when it reproduces twice in fresh browser sessions, is absent
from a control build that lacks that one fault, and survives delta-debugging
minimisation~\cite{zeller2002simplifying}. The measures are kept separate throughout:
\begin{itemize}[noitemsep]
  \item the number of distinct faults verified, for breadth;
  \item the share of runs that verify at least one fault, for reliability;
  \item the interactions until the first verified fault, for speed, with runs that find
        nothing right-censored at the budget;
  \item false positives on clean builds, for credibility.
\end{itemize}

\section{What a functional bug is}
\label{sec:functional-bug}

\paragraph{Fault and failure.} This thesis follows the standard distinction. A \emph{fault}
is a defect in the code. A \emph{failure} is what a user can observe when the faulty code
runs: the application's behaviour departs from what it should do~\cite{barr2015oracle}.
Testers observe failures; the faults behind them are what developers fix. The test
applications here contain known, seeded faults, and the tester's job is to make each one
produce an observable failure and prove it.

\begin{Definition}[Functional bug]
A \emph{functional bug} in a web application is a fault whose failure is an observable
deviation of the application's behaviour from its functional requirements. It must be:
\begin{enumerate}[noitemsep]
  \item \textbf{triggered} by a finite sequence of user interactions (clicks, typed values,
        selections, navigation) from a defined starting state;
  \item \textbf{observable} through what the user can see or what the application keeps:
        page content, the page reached, data shown later, data that persists, or an
        error the browser reports;
  \item \textbf{wrong} against a stated requirement: what the application's own contract
        says it must compute, accept, refuse, store or show.
\end{enumerate}
\end{Definition}

In the terms of ISO/IEC 25010~\cite{iso25010}, a functional bug is a failure of
\emph{functional correctness}: the product does not provide the correct results. It is not a
failure of the non-functional characteristics, so the following are \emph{not} functional
bugs here:
\begin{itemize}[noitemsep]
  \item security vulnerabilities (out of scope, Section~\ref{sec:scope});
  \item performance;
  \item visual layout;
  \item usability;
  \item accessibility.
\end{itemize}
A page that renders slowly or looks wrong but computes, stores and shows the right things
has no functional bug.

\paragraph{A taxonomy.} Every seeded fault in this thesis belongs to one of six classes
(Table~\ref{tab:bug-classes}). Each class corresponds to the assertions the oracle uses to
decide that a failure occurred (Section~\ref{sec:oracle}), so the definition is operational:
for every class, the thesis can state exactly what observation shows the bug.

\paragraph{Why the definition matters for the evaluation.} The first five classes are
\emph{silent}: the page renders, nothing errors, and the result is simply wrong. An implicit
oracle, one that counts console errors as published RL web testers
do~\cite{zheng2021webexplor, gu2025webrled}, cannot see them. Only the last class is visible
to such an oracle. This is why the thesis measures \emph{verified} functional bugs against a
specification of each seeded fault. It is also why the external comparison, which uses the
literature's measures of coverage and console failures, sees only part of what a functional
tester is for.

\section{Objectives}

\begin{enumerate}
  \item Build a browser environment and a deterministic, replay-verified oracle for seeded
        faults that makes false positives measurable and rare.
  \item Build a deep RL tester and test, under pre-registration, whether pretraining on other
        applications transfers to a new one, and whether the network learns which action
        helps in which state.
  \item Measure whether a small, local large language model (LLM) is a useful source of
        reward or page labels for testing.
  \item Use those findings to design a tester whose exploration does not depend on what the
        deep network failed to learn, and evaluate it on held-out applications under
        pre-registration.
  \item Compare the final tester with published RL web testers on their own subject
        applications.
  \item Package the tester as a usable product: a command-line tool and a web interface that
        test a URL, a static site, a Dockerfile repository or a bundled application and
        produce a report with evidence.
\end{enumerate}

\section{Contributions}

The tester built in this thesis, product and research system together, is called
\emph{Katalyze}. It is best described as \emph{an autonomous exploratory testing system with
a verified-fault evaluation pipeline}. The thesis does not claim a new RL algorithm: the
deep Q-network, Thompson sampling, the Go-Explore archive and the test operators all build on
existing ideas~\cite{mnih2015human, russo2018tutorial, ecoffet2021first}. The contributions
fall into three kinds:
\begin{itemize}[noitemsep]
  \item a system that integrates these components;
  \item an evaluation methodology for RL-based functional web testing;
  \item empirical findings, several of them negative.
\end{itemize}
They are:

\begin{enumerate}
  \item \textbf{A verified-fault oracle for web testing.} Each seeded fault has its own
        control build. A candidate counts only if it reproduces twice, does not occur on
        that control, and survives minimisation. The oracle produced zero false positives in
        every clean-build control run of every evaluation.
  \item \textbf{A pre-registered transfer experiment for deep RL web testing}, using
        leave-one-application-out evaluation and censoring-aware statistics. It found no
        measurable benefit from pretraining, with an interval too wide to rule one in or
        out.
  \item \textbf{A pre-registered diagnostic separating contextual learning from
        memorisation.} It uses a generated application family and probe states labelled by
        execution, and shows that the v1 network does not learn context.
  \item \textbf{Two negative results for small local LLMs in testing}, each measured
        against ground truth: as a progress reward, and as a page and control labeller.
  \item \textbf{A hybrid tester} combining page abstraction, an archive with exact return,
        test operators from standard test design, and a light online learner. It was
        evaluated on eight held-out applications under pre-registration, and verified the
        most distinct faults with zero false positives.
  \item \textbf{Sixteen test applications with real backends and seeded faults}, each
        admitted by mechanical checks. The eight development applications run on PostgreSQL
        or MongoDB, with sign-in and crash-type faults.
  \item \textbf{An external comparison with WebExplor and WebRLED} on their own
        applications and measures, in two rounds. The first is a negative result. A post-hoc
        diagnosis identifies action-space completeness, meaning which elements the tester
        can act on, as an important limit on coverage. A pre-registered second round with
        better detection came close to WebExplor's coverage, above it without the
        20-branch Petclinic, and stayed below WebRLED's.
\end{enumerate}

\section{Scope}
\label{sec:scope}

The project began with two agents: one for security testing and one for functional testing.
The security agent was dropped early so that one agent could be built and evaluated end to
end. \textbf{Security testing is out of scope}; this thesis is about functional testing.
The applications are small to medium web applications with seeded faults. Claims about
production sites or real-world fault rates are outside what the evidence supports, and
Chapter~\ref{chap.6} states the limits on generalisation.
