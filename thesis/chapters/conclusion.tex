\section{Conclusion}

This thesis asked whether reinforcement learning can make an automated functional tester for
web applications find verified faults sooner, and under what design. The answer has three
parts.

First, a deep RL tester (v1) learned useful behaviour inside an application, but not in a
way that transferred or used context. Pretraining on five applications did not speed up
discovery on a sixth, and the network ranked actions without regard to whether they helped
in the current state. A small local LLM did not help, either as a progress reward or as a
page labeller; neither generalised beyond the data it was tuned on.

Second, a hybrid tester built around structure rather than learning (page abstraction, an
archive with exact return, test-design operators) verified deep faults that random
exploration missed, with no false positives in any control run. On held-out applications its
arms verified the most distinct faults, though no pre-registered comparison of speed reached
a verdict. Across every evaluation, no learning layer improved on the same structure without
learning.

Third, on WebExplor's own benchmark, measured as the published work measures, the frozen
tester did not reach WebExplor's or WebRLED's coverage or failure counts. A post-hoc
follow-up located much of the gap in the set of elements the tester can act on. With custom
clickables, Phoenix coverage rose from 49\% to WebRLED's 83\% for every arm. Excluding the
20-branch Petclinic, the arms matched or exceeded WebExplor's average, though not WebRLED's.

The evidence therefore supports a modest claim. For finding verified functional faults, the
structure of the tester matters more than the learning in it. For broad reach over an
interface, what a tester can perceive and act on bounds any policy. Learning, as used here
and in the literature it builds on, was not what made the difference.

\section{Limitations}

\begin{itemize}
  \item Each evaluation used six to eight applications, so most comparisons are inconclusive
        and the claims are descriptive.
  \item The development and validation applications and their seeded faults were built
        within the project.
  \item Seeded faults are an incomplete proxy for real faults, and the oracle verifies only
        what was seeded; the specification-free invariants raised false alarms on unsaved
        state.
  \item The external comparison used three repetitions instead of five, different machines,
        and automatic failure deduplication, against published numbers that could not be
        re-run.
  \item Repository intake requires a Dockerfile.
\end{itemize}

\section{Scope for further research}

\begin{itemize}
  \item \textbf{Action space.} Make the custom-clickables scan the default and evaluate it
        under pre-registration, or learn which elements are actionable, as WebRLED does; and
        find what bounds Retroboard.
  \item \textbf{Two deviations in one walk.} Operators that combine two deviations in one
        walk, for the faults no single deviation reaches.
  \item \textbf{Learning across applications.} At the scale the literature suggests (tens of
        applications), with page semantics in the state.
  \item \textbf{Specification-free oracles} that distinguish saved from unsaved state.
  \item \textbf{LLMs off the decision path.} Use them offline, to propose test operators or
        assertions for an application.
\end{itemize}
